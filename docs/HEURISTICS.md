## Severity

| | Meaning |
|---|---|
| **must** | A gate. Ship without it and the plan is wrong. |

## Architecture & decomposition

_Shape of the loop before you write the loop._

### ARCH-01 — Build the simplest thing that could work, then add autonomy

**MUST**

Write down the single-prompt or fixed-workflow version first and the specific failure that forces a loop. If you cannot name the failure, you do not need an agent yet.

**Verify:** A one-page design note states the chosen pattern and cites the observed failure of the simpler alternative.

**Anti-pattern:** Reaching for an orchestration framework before writing the prompt.

**Sources:** [Anthropic 2024](https://www.anthropic.com/engineering/building-effective-agents) · [AI-SDLC 2026](https://ai-sdlc.io/docs/spec/autonomy)

### ARCH-02 — Prefer a workflow with gates over an agent when the trajectory is knowable

**SHOULD**

Encode the steps you already know as a chain, and put a programmatic gate between steps. Reserve model-driven routing for the one step whose shape you genuinely cannot predict.

**Verify:** Each pipeline stage has an explicit exit assertion, and a failing assertion halts rather than retries.

**Sources:** [Anthropic 2024](https://www.anthropic.com/engineering/building-effective-agents) · [AWS Security 2026](https://aws.amazon.com/blogs/security/four-security-principles-for-agentic-ai-systems/)

### ARCH-03 — Route across specialists instead of scaling the tool menu

**SHOULD**

Split into 2–4 routers each holding a small, semantically distinct tool set, and pick the router with a cheap classifier before any model sees the tool list. Confusable neighbours degrade selection faster than tool count does.

**Verify:** Tool-selection accuracy measured per router, not just end-to-end. No router exposes overlapping verbs.

**Sources:** [Anthropic 2024](https://www.anthropic.com/engineering/building-effective-agents) · [arXiv survey 2025](https://arxiv.org/abs/2507.21504)

### ARCH-04 — Delegation is an authorization decision, not an implementation detail

**MUST**

Give each sub-agent its own identity and its own tool allowlist. A child must not inherit the parent's full authority, and the parent must not be able to widen a child's scope at runtime.

**Verify:** An authorization matrix exists mapping agent → allowed tools → data scope, and it is enforced by the runtime rather than by prompt text.

**Sources:** [OWASP AISVS 2026](https://github.com/OWASP/AISVS/blob/main/1.0/en/0x10-C09-Orchestration-and-Agentic-Action.md) · [OWASP Agentic Top 10 2026](https://genai.owasp.org/download/52117/)

### ARCH-05 — Put the safety in the box, not in the prompt

**MUST**

Every constraint that matters must be enforced by code the model cannot edit: an allowlist, a policy engine, a scoped credential, a schema. Prompt-level rules are advisory and will be argued with.

**Verify:** Delete the system prompt and re-run the unsafe-action test suite. Nothing that should be blocked becomes possible.

**Anti-pattern:** "You must never delete files" in a system prompt with a `shell` tool available.

**Sources:** [AWS Security 2026](https://aws.amazon.com/blogs/security/four-security-principles-for-agentic-ai-systems/) · [Google SAIF 2025](https://saif.google/secure-ai-framework/controls)

### ARCH-06 — Cap the loop structurally

**SHOULD**

Long-horizon runs need a checkpointed plan, a resumable state file, and a hard ceiling on iterations per objective. Otherwise a subtle blocker becomes an infinite spend.

**Verify:** Kill a run mid-flight, restart it, and confirm it resumes without repeating side effects.

**Sources:** [Anthropic 2024](https://www.anthropic.com/engineering/building-effective-agents) · [OWASP AISVS 2026](https://github.com/OWASP/AISVS/blob/main/1.0/en/0x10-C09-Orchestration-and-Agentic-Action.md)

## Tooling & agent-computer interface

_The tool surface is the attack surface._

### TOOL-01 — One tool, one verb — never expose a general-purpose shell

**MUST**

Replace `run_command` with the specific operations you actually need (write_file, fetch_issue, post_comment) and make each one refuse anything outside its declared scope. An open-ended executor makes every other control negotiable.

**Verify:** Enumerate the tool list; no tool accepts an arbitrary command string, path glob, or SQL fragment.

**Anti-pattern:** A `bash` tool with an "allowlist" implemented as a regex on the command string.

**Sources:** [OWASP LLM Top 10 2025](https://genai.owasp.org/llm-top-10/) · [MCP spec 2025](https://modelcontextprotocol.io/specification/2025-11-25) · [Anthropic 2024](https://www.anthropic.com/engineering/building-effective-agents)

### TOOL-02 — Closed-world parameter schemas

**SHOULD**

Set `additionalProperties: false`, enumerate enum values instead of free strings, and constrain paths with a pattern. Undeclared arguments must be a hard validation error, not a passthrough.

**Verify:** Fuzz each tool with extra keys, wrong types, and path traversal strings; every call is rejected before reaching the implementation.

**Sources:** [OWASP 2026](https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html) · [MCP spec 2025](https://modelcontextprotocol.io/specification/2025-11-25)

### TOOL-03 — Poka-yoke the interface

**SHOULD**

Make the wrong call hard to express: absolute paths instead of relative, canonical resource IDs instead of names, required `reason` fields, and one obvious way to do each thing. Interface design is where most agent failures are actually fixed.

**Verify:** Run 50 sampled tasks and log tool-call errors. Every repeat error class becomes a schema or naming change, not a prompt tweak.

**Sources:** [Anthropic 2024](https://www.anthropic.com/engineering/building-effective-agents)

### TOOL-04 — Hash and pin the whole tool definition

**MUST**

Hash name + description + inputSchema + outputSchema + annotations together and require re-approval when the hash changes. A flipped `readOnlyHint` changes client approval behaviour without touching the description — this is the rug-pull vector.

**Verify:** Mutate a single annotation in a test tool server; the client refuses to invoke until re-approved, and the diff is shown to the approver.

**Anti-pattern:** Pinning only `description`, or trusting `destructiveHint` for anything.

**Sources:** [OWASP 2026](https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html) · [MCP spec 2025](https://modelcontextprotocol.io/specification/2025-11-25)

### TOOL-05 — Errors are an interface, not a stack trace

**SHOULD**

Return typed, bounded, actionable errors (what failed, what the valid options are, whether retrying helps) and mark them as tool errors rather than protocol errors so the model can self-correct instead of looping.

**Verify:** A forced-failure test shows the agent recovers within one retry for recoverable errors and stops immediately for terminal ones.

**Sources:** [MCP spec 2025](https://modelcontextprotocol.io/specification/2025-11-25) · [Anthropic 2024](https://www.anthropic.com/engineering/building-effective-agents)

### TOOL-06 — Every mutating tool gets a dry-run mode

**MUST**

Implement `dry_run: true` that returns the exact diff, recipients, or resource deltas the real call would produce. This is what makes an approval prompt meaningful instead of a rubber stamp.

**Verify:** For each mutating tool, dry-run then real-run against a fixture; the diff predicted equals the diff applied.

**Sources:** [OWASP AISVS 2026](https://github.com/OWASP/AISVS/blob/main/1.0/en/0x10-C09-Orchestration-and-Agentic-Action.md) · [OWASP Agentic Top 10 2026](https://genai.owasp.org/download/52117/)

### TOOL-07 — Idempotency keys on state changes

**SHOULD**

When you cannot undo an action, make it safe to repeat: client-supplied idempotency keys, de-duplication windows, and an explicit "already done" response. Retries are the most common cause of doubled side effects.

**Verify:** Replay the same tool call three times; exactly one side effect appears and the response is stable.

**Sources:** [OWASP 2026](https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html)

### TOOL-08 — Keep the tool set small enough to test exhaustively

**SHOULD**

Above roughly 20 tools you can no longer hand-verify selection behaviour. Add per-tool eval cases — at minimum one positive, one near-miss, and one adversarial case — before the tool ships.

**Verify:** CI fails if a new tool lands without three associated eval cases.

**Sources:** [arXiv survey 2025](https://arxiv.org/abs/2507.21504) · [Anthropic 2024](https://www.anthropic.com/engineering/building-effective-agents)

## Sandboxing & execution isolation

_Where untrusted actions land, and what bounds them._

### SBX-01 — Isolation floor matches the execution surface

**MUST**

Target isolation tier S2 or better. Tier below this is not a defensible boundary for the actions described.

**Verify:** Document the isolation primitive in use (process, container, microVM, dedicated host) and the kernel boundary it relies on.

**Sources:** [UK AISI 2026](https://arxiv.org/abs/2603.02277) · [AWS Security 2026](https://aws.amazon.com/blogs/security/four-security-principles-for-agentic-ai-systems/)

### SBX-02 — Deny egress by default

**MUST**

Default-deny outbound traffic and allow only named destinations through a proxy that logs. Exfiltration requires egress; removing it converts a data-loss incident into a failed request.

**Verify:** Curl an unlisted host from inside the sandbox and confirm it fails closed, with the attempt logged.

**Anti-pattern:** An "allowlist" that is really a firewall rule allowing 0.0.0.0/0 on 443.

**Sources:** [OWASP Agentic Top 10 2026](https://genai.owasp.org/download/52117/) · [Willison 2025](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)

### SBX-03 — No privileged mode, no host mounts, no daemon socket

**MUST**

Run non-root, read-only root filesystem, all capabilities dropped, no `--privileged`, no bind-mount of the host Docker socket, no `hostPath` volumes. These are the specific misconfigurations frontier models exploit within minutes.

**Verify:** Attempt the standard escape set (privileged, host mount, socket reach, writable /proc/sys) in a test run; all must fail.

**Sources:** [UK AISI 2026](https://arxiv.org/abs/2603.02277)

### SBX-04 — Ephemeral filesystem, fresh per run

**SHOULD**

Give each run a disposable overlay. State that must persist lives in an explicitly mounted, narrowly scoped volume — everything else disappears with the run.

**Verify:** Two consecutive runs cannot see each other's files.

**Sources:** [UK AISI 2026](https://arxiv.org/abs/2603.02277) · [Qing et al. 2026](https://arxiv.org/abs/2606.01317)

### SBX-05 — Kernel-level resource caps

**MUST**

Cap CPU, memory, disk, PID count, wall-clock, and open file descriptors per execution. An uncapped sandbox is a denial-of-service primitive against your own host.

**Verify:** A fork bomb and a 10 GB write both fail at the configured limit without degrading other tenants.

**Sources:** [OWASP AISVS 2026](https://github.com/OWASP/AISVS/blob/main/1.0/en/0x10-C09-Orchestration-and-Agentic-Action.md)

### SBX-06 — Plain container isolation is not sufficient on its own

**MUST**

Where the agent is capable and touches secrets or consequential systems, put the container inside a VM (microVM, gVisor, Kata) or a dedicated host, with a network proxy on the boundary. Treat the container as packaging, and the hypervisor as the security boundary.

**Verify:** A sandbox-escape CTF run against your own configuration, with the flag on the host, produces zero successes.

**Anti-pattern:** Assuming "it is in Docker" is an isolation argument.

**Sources:** [UK AISI 2026](https://arxiv.org/abs/2603.02277) · [Google Research 2025](https://arxiv.org/abs/2502.17832)

### SBX-07 — Credentials never enter the model context

**MUST**

Inject short-lived credentials into the tool executor, not the prompt. The model should name a capability ("read the repo"); the runtime should hold the token. Anything in the context window is one injection away from being exfiltrated.

**Verify:** Scan every outbound model request and every trace for secret-shaped strings; zero hits.

**Sources:** [OWASP AISVS 2026](https://github.com/OWASP/AISVS/blob/main/1.0/en/0x10-C09-Orchestration-and-Agentic-Action.md) · [Google SAIF 2025](https://saif.google/secure-ai-framework/controls)

### SBX-08 — Adversarially test your own sandbox configuration

**SHOULD**

Run a container-escape CTF against your own deployment on a schedule, in a nested sandbox so a success does not compromise the host. Misconfiguration, not kernel exploits, is the realistic failure mode.

**Verify:** Benchmark results are recorded per release with a named owner and a remediation SLA for any success.

**Sources:** [UK AISI 2026](https://arxiv.org/abs/2603.02277)

### SBX-09 — Broker credentials per call rather than shipping them into the sandbox

**SHOULD**

Move to a broker that issues a narrowly scoped token for the duration of one tool call. Ambient env vars are readable by anything running in that environment, including injected code, and they typically outlive the incident.

**Verify:** Kill the credential injection path and confirm tools fail closed with a clear authorization error rather than falling back to a cached token.

**Sources:** [OWASP AISVS 2026](https://github.com/OWASP/AISVS/blob/main/1.0/en/0x10-C09-Orchestration-and-Agentic-Action.md) · [Google SAIF 2025](https://saif.google/secure-ai-framework/controls)

## Authority, identity & permissions

_Deterministic enforcement outside the model._

### AUTH-01 — Least agency: cut tools, then permissions, then autonomy

**MUST**

In that order. Delete every tool the use case does not need, shrink each remaining tool's scope to the narrowest verb and data set, and only then decide how much autonomy the residual surface justifies. Most excessive-agency findings are removable functionality, not tunable settings.

**Verify:** A table lists each tool, its justification, its scope, and the use case that would break if it were removed.

**Anti-pattern:** Keeping an admin tool "in case the agent needs it later".

**Sources:** [OWASP LLM Top 10 2025](https://genai.owasp.org/llm-top-10/) · [Google SAIF 2025](https://saif.google/secure-ai-framework/controls) · [MCP spec 2025](https://modelcontextprotocol.io/specification/2025-11-25)

### AUTH-02 — One policy enforcement point for every tool call

**MUST**

Funnel all invocations through a single gateway that validates actor, tool, target, and normalized parameters against policy, then issues the scoped credential. Complete mediation means there is no second path — no direct SDK call, no cached token, no debug bypass.

**Verify:** Grep the codebase: no tool implementation is reachable except through the gateway; the gateway is the only holder of downstream credentials.

**Sources:** [AWS Security 2026](https://aws.amazon.com/blogs/security/four-security-principles-for-agentic-ai-systems/) · [OWASP AISVS 2026](https://github.com/OWASP/AISVS/blob/main/1.0/en/0x10-C09-Orchestration-and-Agentic-Action.md)

### AUTH-03 — Bind approvals to the exact action, and consume them atomically

**MUST**

The approval record carries actor + tool + target + normalized params + timestamp + expiry, is single-use, and is checked-and-consumed in one step immediately before execution. A `user_confirmed: true` boolean is not authorization. Any parameter change requires fresh approval.

**Verify:** Replay a consumed approval; it must fail. Mutate one parameter after approval; it must fail. Swap the actor; it must fail.

**Anti-pattern:** Approve-in-the-UI, then execute from a worker with no linkage between the two.

**Sources:** [OWASP 2026](https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html) · [OWASP AISVS 2026](https://github.com/OWASP/AISVS/blob/main/1.0/en/0x10-C09-Orchestration-and-Agentic-Action.md)

### AUTH-04 — Classify reversibility at runtime and enforce it

**SHOULD**

Tag each action read-only / reversible / externally-reversible / irreversible, and let the tag drive the gate: proceed, proceed-and-notify, require approval, require step-up auth. In a multi-step chain, the whole chain inherits its most irreversible step.

**Verify:** Every tool has a reversibility classification, and a test asserts the gate behaviour for each class.

**Sources:** [OWASP AISVS 2026](https://github.com/OWASP/AISVS/blob/main/1.0/en/0x10-C09-Orchestration-and-Agentic-Action.md)

### AUTH-05 — Separate the component that proposes from the component that executes

**MUST**

The agent emits a structured intent. An independent service validates scope, privilege, and approval state, then performs the action with credentials the agent never holds. This also blocks the "approve one thing, execute another" (TOCTOU) class.

**Verify:** Revoke the agent's direct credential for the target system; the workflow must still work through the executor and fail closed if the executor rejects.

**Sources:** [OWASP AISVS 2026](https://github.com/OWASP/AISVS/blob/main/1.0/en/0x10-C09-Orchestration-and-Agentic-Action.md) · [AWS Security 2026](https://aws.amazon.com/blogs/security/four-security-principles-for-agentic-ai-systems/)

### AUTH-06 — Act in the user's authority, not a service account's

**SHOULD**

Propagate an integrity-protected, scope-limited token carrying the requesting user's authorization, and enforce it at each downstream hop. A shared high-privilege service identity makes every user able to reach every other user's data.

**Verify:** Run the same task as two users with different entitlements; each sees only its own data, and the difference is enforced downstream.

**Sources:** [OWASP AISVS 2026](https://github.com/OWASP/AISVS/blob/main/1.0/en/0x10-C09-Orchestration-and-Agentic-Action.md) · [Google SAIF 2025](https://saif.google/secure-ai-framework/controls) · [MCP 2025](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices)

### AUTH-07 — Block self-modification of tools, policy, and memory schema

**MUST**

The agent may propose a new tool or prompt change; it may not install one. Promotion goes through human review with the same hash-pinning as any other tool. Runtime self-expansion of capability invalidates your threat model by construction.

**Verify:** Attempt to add a tool at runtime; the runtime rejects it and logs an alert.

**Sources:** [OWASP AISVS 2026](https://github.com/OWASP/AISVS/blob/main/1.0/en/0x10-C09-Orchestration-and-Agentic-Action.md) · [OWASP Agentic Top 10 2026](https://genai.owasp.org/download/52117/)

### AUTH-08 — Fail closed on ambiguity

**MUST**

Unknown tool, unresolvable alias, missing risk classification, expired approval, failed policy lookup, or failed audit write must all block. Never fall back to "allow" because a dependency was unavailable.

**Verify:** Inject a fault into each dependency in the tool path; every one results in a blocked call, not a permitted one.

**Sources:** [OWASP 2026](https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html) · [OWASP Agentic Top 10 2026](https://genai.owasp.org/download/52117/)

## Human oversight

_Making review possible rather than decorative._

### OVR-01 — Oversight must be catchable, not nominal

**MUST**

A reviewer who cannot see the action before it lands, or cannot understand it, is not a control — they are a signature. Either move the review point earlier and make it informative, or drop the pretence and replace it with deterministic gating.

**Verify:** Timed test: a reviewer is shown a synthetic bad action and must identify it in under 60 seconds using only what the interface surfaces.

**Anti-pattern:** A post-hoc log review standing in for approval on an irreversible action.

**Sources:** [Mitchell 2026](https://arxiv.org/abs/2608.23642) · [EU AI Act 2024](https://eur-lex.europa.eu/eli/reg/2024/1689/oj)

### OVR-02 — Budget the human's attention, not just the agent's tokens

**MUST**

Above roughly 20 review points per person per day, approval becomes a reflex and the control inverts: it manufactures false assurance while costing real time. Batch low-risk actions behind an exception summary, reserve individual prompts for genuinely irreversible ones, and measure approval latency and rejection rate as health metrics.

**Verify:** Dashboard tracks approvals/hour, median decision time, and rejection rate per reviewer. A rejection rate near zero is a red flag, not a success.

**Sources:** [Mitchell 2026](https://arxiv.org/abs/2608.23642) · [Knight Institute 2025](https://knightcolumbia.org/content/levels-of-autonomy-for-ai-agents-1)

### OVR-03 — Render approval previews from trusted objects, never from model text

**MUST**

The approval dialog is generated from the canonical action object the executor will validate, with model- and tool-supplied strings escaped and shown in bounded fields. Otherwise injected content can reshape what the approver believes they are approving ("lies in the loop").

**Verify:** Inject adversarial text into a tool result and confirm the approval UI shows the real command, diff, recipient, and amount unchanged.

**Sources:** [OWASP AISVS 2026](https://github.com/OWASP/AISVS/blob/main/1.0/en/0x10-C09-Orchestration-and-Agentic-Action.md) · [OWASP 2026](https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html)

### OVR-04 — Match the review tier to the risk class

**SHOULD**

Tier it: read-only proceeds silently; reversible proceeds with notification; irreversible needs approval; anything touching money, entitlements, or safety needs approval plus step-up authentication. Uniform prompting trains reviewers to click through.

**Verify:** The action taxonomy is written down, every tool maps to a class, and unmapped tools default to the highest tier.

**Sources:** [OWASP 2026](https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html) · [Cloud Security Alliance 2026](https://cloudsecurityalliance.org/blog/2026/01/28/levels-of-autonomy)

### OVR-05 — The reviewer must be able to be wrong

**SHOULD**

If the reviewer cannot independently evaluate the action, oversight is theatre. Either raise reviewer competence with a domain-specific checklist and training, or reduce the action set until a non-expert can meaningfully judge it.

**Verify:** A reviewer-written justification exists for a sample of 20 approvals, showing what they checked.

**Sources:** [Mitchell 2026](https://arxiv.org/abs/2608.23642) · [EU AI Act 2024](https://eur-lex.europa.eu/eli/reg/2024/1689/oj)

### OVR-06 — Name a human owner

**MUST**

A specific person, not a distribution list, is accountable for this agent's behaviour and is the escalation target when it misbehaves. Distribution lists do not answer pages.

**Verify:** The owner appears in the service catalogue, the on-call rotation, and the incident runbook.

**Sources:** [NIST 2023](https://www.nist.gov/itl/ai-risk-management-framework) · [ISO/IEC 2023](https://www.iso.org/standard/42001) · [AWS 2025](https://aws.amazon.com/ai/security/agentic-ai-scoping-matrix/)

## Budgets, loops & shutdown

_Bounding runtime, spend, and blast._

### BUD-01 — Hard caps on steps, tokens, and money — enforced by the runtime

**MUST**

Per-run ceilings on iterations, input+output tokens, and currency, checked in the loop rather than estimated afterwards. On breach: halt, snapshot state, and surface a resumable plan. Cost is a safety property because it is the failure mode that gets noticed last.

**Verify:** A deliberately looping fixture halts at the configured cap and emits a cost-exceeded event.

**Sources:** [OWASP AISVS 2026](https://github.com/OWASP/AISVS/blob/main/1.0/en/0x10-C09-Orchestration-and-Agentic-Action.md) · [OpenTelemetry 2026](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-metrics.md)

### BUD-02 — Bound recursion and fan-out

**MUST**

Max delegation depth, max concurrent children, and a shared budget the children draw from. Unbounded fan-out turns a small reasoning slip into a spend event measured in hours.

**Verify:** A test agent instructed to spawn helpers recursively terminates at the configured depth with a clear error.

**Sources:** [OWASP AISVS 2026](https://github.com/OWASP/AISVS/blob/main/1.0/en/0x10-C09-Orchestration-and-Agentic-Action.md) · [OWASP Agentic Top 10 2026](https://genai.owasp.org/download/52117/)

### BUD-03 — Per-tool rate limits and quotas

**SHOULD**

Limits belong on the tool, not the model: N calls/minute, M writes/hour, one bulk operation per run. This is what converts "the agent went haywire" from an incident into a logged rejection.

**Verify:** A burst test exceeds the quota and receives 429-equivalent responses the agent handles gracefully.

**Sources:** [MCP spec 2025](https://modelcontextprotocol.io/specification/2025-11-25) · [OWASP AISVS 2026](https://github.com/OWASP/AISVS/blob/main/1.0/en/0x10-C09-Orchestration-and-Agentic-Action.md)

### BUD-04 — Out-of-band kill switch

**MUST**

A halt path that does not run through the agent, its host, or its credentials — a control-plane flag the executor checks before every action. Ctrl-C on a shared terminal is not a kill switch, and an agent that can reach the switch can decline to use it.

**Verify:** Trigger the switch mid-run; the next tool call is refused within one call, and the state is inspectable.

**Sources:** [OWASP AISVS 2026](https://github.com/OWASP/AISVS/blob/main/1.0/en/0x10-C09-Orchestration-and-Agentic-Action.md) · [AWS Security 2026](https://aws.amazon.com/blogs/security/four-security-principles-for-agentic-ai-systems/)

### BUD-05 — Timeouts on every tool call

**MUST**

A timeout plus a bounded retry policy with jitter, and a terminal state that the agent can reason about. Without it a single hung dependency silently consumes the entire run budget.

**Verify:** A black-holed tool endpoint causes a clean timeout error within the configured window.

**Sources:** [MCP spec 2025](https://modelcontextprotocol.io/specification/2025-11-25)

### BUD-06 — Alert on spend rate, not just spend total

**CONSIDER**

Track cost per run and per user, and alert on the derivative. A step change in cost-per-task usually means the agent started looping before the absolute budget trips.

**Verify:** Cost per successful task is charted with a weekly baseline and an alert on >2σ deviation.

**Sources:** [OpenTelemetry 2026](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-metrics.md)

## Observability & audit

_If it is not recorded, it did not happen._

### OBS-01 — Emit a span per agent invocation and per tool execution

**SHOULD**

Follow the OpenTelemetry GenAI conventions: `invoke_agent` spans with `gen_ai.agent.name`, `execute_tool` spans with `gen_ai.tool.name`, and a shared `gen_ai.conversation.id`. Standard attributes mean off-the-shelf tooling works and you are not writing bespoke dashboards.

**Verify:** A single run produces a trace with a parent agent span and one child span per tool call, joinable by conversation id.

**Sources:** [OpenTelemetry 2026](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md)

### OBS-02 — Record tool arguments and results — deliberately

**SHOULD**

Log the arguments and results that justify a decision, with secret redaction applied before the record is written. These attributes are opt-in in the spec precisely because they are sensitive; treat the log as production data.

**Verify:** Replay a historical trace and reconstruct exactly why an action was taken, without needing the original conversation.

**Sources:** [OpenTelemetry 2026](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md)

### OBS-03 — Immutable audit trail for state changes

**MUST**

Append-only, tamper-evident, retained per your obligations: who approved, what was proposed, what executed, what changed. Written by the executor, not the agent, so the agent cannot omit its own mistakes.

**Verify:** Attempt to delete or modify an audit record from the agent's credential; it must be denied.

**Sources:** [NIST 2023](https://www.nist.gov/itl/ai-risk-management-framework) · [OWASP AISVS 2026](https://github.com/OWASP/AISVS/blob/main/1.0/en/0x10-C09-Orchestration-and-Agentic-Action.md) · [Google SAIF 2025](https://saif.google/secure-ai-framework/controls)

### OBS-04 — Alert on tool-chain shape, not error rate

**MUST**

The signature of exfiltration is a sequence — read sensitive source, then call an outbound tool — not an error. Alert on the pattern, with the egress destination attached. Error rates stay flat during the worst incidents.

**Verify:** A synthetic read-sensitive-then-post-external sequence fires an alert within one run.

**Sources:** [OWASP Agentic Top 10 2026](https://genai.owasp.org/download/52117/) · [Willison 2025](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)

### OBS-05 — Attribute cost and tokens per run and per tenant

**CONSIDER**

Record input, output, and cached tokens per span so cost can be attributed after the fact. Multi-tenant agents without attribution become a budgeting argument you cannot win.

**Verify:** Monthly spend reconciles to the sum of per-run attributed cost within a stated tolerance.

**Sources:** [OpenTelemetry 2026](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-metrics.md)

## Evaluation & release gates

_Capability is not reliability. Measure both._

### EVAL-01 — No meaningful autonomy without a labelled evaluation set

**MUST**

Build 30–100 real cases with expected end states before granting write access. Without this you cannot distinguish "it works" from "it has not failed yet", and every change is an unmeasured risk.

**Verify:** The eval set runs in CI, is versioned with the prompt, and its cases came from production traffic or domain review.

**Sources:** [NIST 2024](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf) · [arXiv survey 2025](https://arxiv.org/abs/2507.21504)

### EVAL-02 — Report pass^k, not pass@1

**MUST**

Run each task k times (k≥4) and report the fraction of tasks where all k succeeded. pass@k flatters you; pass^k is what a user experiences. Published results show strong agents dropping from ~60% to under 25% at k=8 — capability is not reliability.

**Verify:** Eval reports include pass@1, pass^4, and the per-task variance, with the trial count in the output.

**Sources:** [Yao et al. 2024](https://arxiv.org/abs/2406.12045) · [arXiv survey 2025](https://arxiv.org/abs/2507.21504)

### EVAL-03 — Score the end state, not the transcript

**MUST**

Grade the resulting workspace or database against an expected state. A confident, well-formatted wrong answer scores identically to a confident right one when you only read the message.

**Verify:** Each eval case declares a machine-checkable expected end state and a diff of actual versus expected.

**Sources:** [Qing et al. 2026](https://arxiv.org/abs/2606.01317) · [Yao et al. 2024](https://arxiv.org/abs/2406.12045)

### EVAL-04 — Detect corrupt success

**MUST**

Score procedure as well as outcome: did it follow the policy, call the required tools, ask for the confirmation? Reported success rates overstate real safety substantially — a large share of "passes" are passes achieved by skipping a required step.

**Verify:** Every eval case has both an outcome assertion and a procedure assertion; a case that passes outcome but fails procedure is reported as a failure.

**Sources:** [Cao et al. 2026](https://arxiv.org/abs/2603.03116)

### EVAL-05 — Test consistency under perturbation, not just accuracy on the base set

**SHOULD**

Perturb format, ordering, and information access, then measure how much the action sequence drifts. Consistency splits into composition drift (picking different tools) and ordering drift (same tools, wrong sequence) — they have different fixes.

**Verify:** Eval reports trajectory consistency alongside accuracy for at least three perturbation families.

**Sources:** [Raj et al. 2026](https://arxiv.org/abs/2605.10516)

### EVAL-06 — Red-team every untrusted channel, not just the chat box

**MUST**

For each channel that can carry text into the context — web page, email, uploaded file, issue comment, tool result, another agent — write an indirect injection case with an observable target action, and assert the action is refused. Tag-stripping and pattern filters are alerts, not enforcement.

**Verify:** An injection suite runs per channel in CI and fails the build on any successful hijack.

**Sources:** [OWASP LLM Top 10 2025](https://genai.owasp.org/llm-top-10/) · [OWASP 2026](https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html) · [NIST 2024](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.100-2e2023.pdf)

### EVAL-07 — Measure the safety-violation rate on the workspace

**MUST**

Score final environment state for destructive filesystem changes, secret exposure, and unauthorised access — separately from task success. Benchmarks on realistic workspaces find even the best coding agents fully safe on well under half of tasks.

**Verify:** Eval output includes a harmful-safety-violation rate per model and per prompt version, tracked over releases.

**Sources:** [Qing et al. 2026](https://arxiv.org/abs/2606.01317)

### EVAL-08 — Prompts, tools, and models only change through a gate

**SHOULD**

Version the prompt, tool schemas, and model id together as one artifact, and gate deploys on the eval suite. Swapping a model version is a behaviour change, not a dependency bump.

**Verify:** A PR changing the prompt or model id cannot merge without eval results attached.

**Sources:** [arXiv survey 2025](https://arxiv.org/abs/2507.21504) · [NIST 2023](https://www.nist.gov/itl/ai-risk-management-framework)

## Supply chain & provenance

_Models, servers, and tool definitions you did not write._

### SUPPLY-01 — Vet, pin, and sandbox third-party tool servers

**MUST**

Pin by version and hash, run in its own container with its own scoped identity, grant no shared token across servers, and re-review on any definition change. A tool server is arbitrary code execution with your credentials attached.

**Verify:** Each server has a pinned hash, a container image digest, and a distinct credential.

**Sources:** [OWASP 2026](https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html) · [MCP 2025](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices) · [OWASP LLM Top 10 2025](https://genai.owasp.org/llm-top-10/)

### SUPPLY-02 — Maintain a bill of materials for models, tools, and data

**SHOULD**

An AI-BOM listing model ids and versions, tool server versions and hashes, datasets or retrieval corpora, and licences. This is what lets you answer "are we affected?" in minutes rather than days.

**Verify:** The BOM is generated from the deployment artifacts, not maintained by hand.

**Sources:** [OWASP LLM Top 10 2025](https://genai.owasp.org/llm-top-10/) · [NIST 2024](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf)

### SUPPLY-03 — Pin the model and record provenance

**CONSIDER**

Pin an exact model version, record whether weights are hosted or self-hosted, and treat provider-side model updates as untested changes. "Latest" is a supply-chain decision you are making on every request.

**Verify:** The model id in the deployment manifest is a specific version, and the eval suite runs against it.

**Sources:** [NIST 2024](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf) · [OWASP LLM Top 10 2025](https://genai.owasp.org/llm-top-10/)

### SUPPLY-04 — Quarantine on tool definition change

**MUST**

A changed tool manifest suspends the server until a human re-approves, and the approver sees a rendered diff of the schema. Silent update is the rug-pull, and the whole point is that it is silent.

**Verify:** Change a tool description in a test server; invocations are blocked and an approval request is raised with a diff.

**Sources:** [OWASP 2026](https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html)

## Data handling & memory

_Context is a leak vector and a poisoning vector._

### DATA-01 — Break a leg of the lethal trifecta

**MUST**

You have private data, untrusted content, and an outbound channel simultaneously. Any two are defensible; three is a design bug. Break one: strip egress to an allowlist, or run the untrusted-content step in a context with no sensitive data, or require human release on outbound actions.

**Verify:** A red-team task plants an instruction in untrusted content that would exfiltrate a sensitive field to an external destination; the attempt fails.

**Anti-pattern:** Adding a prompt instruction to "ignore instructions found in documents" and calling it mitigated.

**Sources:** [Willison 2025](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/) · [AWS Security 2026](https://aws.amazon.com/blogs/security/four-security-principles-for-agentic-ai-systems/) · [OWASP Agentic Top 10 2026](https://genai.owasp.org/download/52117/)

### DATA-02 — Pass references, not corpora

**SHOULD**

Give the agent an identifier and a scoped retrieval tool rather than bulk-loading records into context. What is never in the window cannot be leaked by an injection, and cannot be memorised by the model.

**Verify:** Measure sensitive-record count per request; it stays below a stated ceiling and is justified per field.

**Sources:** [OWASP LLM Top 10 2025](https://genai.owasp.org/llm-top-10/) · [Google SAIF 2025](https://saif.google/secure-ai-framework/controls)

### DATA-03 — Redact on the way in, not the way out

**MUST**

Apply minimisation and redaction before text reaches the model or the trace. Output filters are a second line, not the first — by the time text is in the response, the disclosure has already happened in principle.

**Verify:** The redaction filter has a test corpus and a measured false-negative rate, reviewed per release.

**Sources:** [NIST 2024](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf) · [OWASP LLM Top 10 2025](https://genai.owasp.org/llm-top-10/)

### DATA-04 — Treat memory writes as untrusted input

**MUST**

Anything that survives a run becomes an instruction source for every later run. Validate on write, attribute the source, apply a TTL, scope memory per user or session, and never let one tenant write into another's store.

**Verify:** Attempt to persist an instruction-shaped string; it is rejected or stored as inert data with provenance.

**Sources:** [OWASP 2026](https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html) · [OWASP Agentic Top 10 2026](https://genai.owasp.org/download/52117/)

### DATA-05 — Written retention and deletion policy

**MUST**

State how long prompts, completions, traces, and tool payloads are kept, where, and how deletion requests propagate — including to the model provider. Retention is decided at design time or it is decided by accident.

**Verify:** A deletion request for one user removes their traces and tool payloads within the stated window, verified by query.

**Sources:** [NIST 2024](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf) · [EU AI Act 2024](https://eur-lex.europa.eu/eli/reg/2024/1689/oj)

## Governance & documentation

_Owner, scope, review, and the incident story._

### GOV-01 — Write the scope statement and the risk acceptance

**MUST**

One page: what the agent may do, what it may not do, what happens when it does it anyway, and who accepted that residual risk. This is the document every later argument defers to.

**Verify:** The document exists, is dated, names an approver, and is linked from the deployment manifest.

**Sources:** [NIST 2023](https://www.nist.gov/itl/ai-risk-management-framework) · [ISO/IEC 2023](https://www.iso.org/standard/42001)

### GOV-02 — Autonomy is earned and can be revoked

**MUST**

Start at the lowest usable tier, define the quantitative evidence required to move up (eval results, incident history, review rejection rate), require re-review for promotion, and demote automatically on regression. No automatic promotion through good behaviour.

**Verify:** A written promotion ladder exists with numeric thresholds, and the current tier is displayed wherever the agent is operated.

**Sources:** [AI-SDLC 2026](https://ai-sdlc.io/docs/spec/autonomy) · [Knight Institute 2025](https://knightcolumbia.org/content/levels-of-autonomy-for-ai-agents-1) · [AWS 2025](https://aws.amazon.com/ai/security/agentic-ai-scoping-matrix/)

### GOV-03 — An incident runbook that mentions the agent

**SHOULD**

It must cover: halt it, identify the run, enumerate what it touched, revert what can be reverted, notify, and preserve logs. "Did the agent do this?" should be answerable in minutes from the audit trail.

**Verify:** A tabletop exercise answers "which runs touched resource X last Tuesday" without engineering help.

**Sources:** [NIST 2023](https://www.nist.gov/itl/ai-risk-management-framework) · [ISO/IEC 2023](https://www.iso.org/standard/42001)

### GOV-04 — Document oversight to the standard the regulator will apply

**MUST**

Article 14 expects oversight that is possible, informed, and effective — including the ability to intervene or halt. Document the oversight design, the reviewer's information, the intervention mechanism, and the evidence that reviewers actually used it.

**Verify:** An oversight record exists per deployment, and a sample of approvals shows a human decision with a stated basis.

**Sources:** [EU AI Act 2024](https://eur-lex.europa.eu/eli/reg/2024/1689/oj) · [NIST 2024](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf)

### GOV-05 — Change control covers prompts, tools, and memory schema

**SHOULD**

Treat prompt text, tool schemas, and memory structure as versioned configuration with review. A prompt edit is a behavioural deploy and deserves the same gate as a code change.

**Verify:** Version control shows prompt and schema history with reviewer attribution and linked eval runs.

**Sources:** [NIST 2023](https://www.nist.gov/itl/ai-risk-management-framework) · [arXiv survey 2025](https://arxiv.org/abs/2507.21504)

## Tier ladders

### Autonomy

| Tier | Name | Human role | Definition | Mappings |
|---|---|---|---|---|
| T0 | Observe | Operator — human performs every action | Read-only. Produces analysis, recommendations, or drafts. No side effects reach a system of record. | AWS: Scope 1 — No agency; CSA: L0/L1; Knight: L1–L2 |
| T1 | Approve | Approver — human approves each side-effecting action | Proposes actions; each one is presented and approved before execution. Approval is bound to the parameters. | AWS: Scope 2 — Prescribed agency; CSA: L1; Knight: L2–L3 |
| T2 | Supervise | Consultant — human approves a plan, then watches and can interrupt | Executes an approved plan inside a bounded envelope, notifying on each consequential step. Exceptions escalate. | AWS: Scope 3 — Supervised agency; CSA: L2; Knight: L3 |
| T3 | Bounded | Collaborator — human sets the envelope and handles exceptions | Autonomous within a machine-enforced envelope (tools, destinations, data classes, budgets). Anything outside it halts and asks. | AWS: Scope 3 — Supervised agency (upper bound); CSA: L3; Knight: L4 |
| T4 | Self-directing | Observer — human monitors and holds the off-switch | Self-initiating, continuous, sets its own sub-goals. Humans review after the fact and can halt. | AWS: Scope 4 — Full agency; CSA: L4–L5; Knight: L5 |

### Sandbox

| Tier | Name | Provides |
|---|---|---|
| S0 | None | No execution. The agent only calls typed APIs through the policy gateway. |
| S1 | Process | Dedicated unprivileged user, seccomp/landlock, no network, cgroup limits. Suitable for trusted, reviewed code only. |
| S2 | Hardened container | Non-root, read-only rootfs, all caps dropped, no privileged mode, no host mounts, no daemon socket, default-deny egress via proxy. |
| S3 | VM / microVM | Container inside a microVM (Firecracker, gVisor, Kata) or a full VM, with a logging egress proxy and ephemeral disk. Kernel boundary is the security boundary. |
| S4 | Dedicated host | Single-tenant hardware, no shared kernel, hardware-isolated. For production credentials, safety-relevant actions, or adversarial red-team work. |
